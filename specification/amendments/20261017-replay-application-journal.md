# Controlled amendment 15 — explicit replay application recovery input

C07 source integration review exposed an external input missing from the closed schema-1 Replay: a real application recovery callback can occur between a rejected resume while interrupted and a later accepted resume. The callback changes application lifecycle without changing Snapshot authority. Replaying only the recorded Commands cannot reproduce that trace. Inferring recovery from an expected receipt would fabricate an input. This controlled amendment closes that representation gap before any C07 acceptance.

Section 03 now defines the separately supplied, closed schema-1 `ReplayApplicationJournal`: `{schema_version:1,replay_sha256,initial_application_state,initial_interruption_reason,recoveries}`. Recovery rows contain only `{before_command_index,operation_tick}`. The journal binds SHA-256 of the complete canonical Replay; its complete canonical hash is required in the replay report and evidence whenever supplied, including an empty recovery list. Evidence retains both exact artifacts. Existing Snapshot, Command, Replay and player-save shapes and schema versions do not change.

The initial phase/lifecycle matrix is explicit: planning starts paused, terminal starts at outcome, and active/stabilizing may start running, paused or with a matching recorded interruption/loading reason. The actual `Interrupt` API establishes the latter on fresh restored domain owners without changing any canonical authority. Normal player load still returns to paused Continue. Recovery records have strictly increasing unique command indexes below the command count, match that command's admission operation tick, and are consumed once immediately before that actual command. The real `RecoverInterruption` API must succeed from an owned interruption. Missing, wrong, duplicate, unused or surplus input fails with a precise reason.

The default runner supplies no recovery input. An active/stabilizing start can use at most two actual independent traces from the same authority, running then paused; planning and outcome have deterministic starts. Only actual receipt, checkpoint and terminal comparisons can pass. An explicit journal selects one validated initial lifecycle and its exact recovery sequence. Neither path injects expected state or infers recovery from expected results. Recording comes from the actual lifecycle controller and successful recovery callbacks; no wall time, live gesture, room/camera/pose data or domain continuation state enters the journal.

The existing C07 native fixture must record a tracking pause, rejected resume, real recovery and accepted resume, then prove exact replay with the journal and failure for missing/wrong/surplus records. Native execution remains pending. This amendment changes no task/check/case definitions, acceptance thresholds, runtime arithmetic/order, content/rules versions, storage budgets or full five-world/25-mission scope. Specification validation is not native, Android, physical-device, human or release qualification.

Exact prior plan, index, runtime contract and seal bytes are preserved under `evidence/runtime-persistence-20261017/replay-amendment-inputs`. The amendment 14 seal is archived byte-for-byte at `specification/archive/freeze_manifest-1.1.0-amendment-14.json`. Only the three amended sealed inputs and the new amendment/archive records are resealed; all other sealed records and earlier archives retain their exact hashes.
